What the log update is

The log update is the process that keeps ECB's project files accurate. Claude scans everything that's happened since the last update — meeting transcripts, Slack, recent chats — pulls out the tasks, decisions, risks, and completions, and rebuilds the files the rest of the system reads from.

Those files are the company's working memory. Every agenda, every MIR, every briefing is only as accurate as they are. The log update is what keeps that memory current — without it, the files slowly drift out of date and everything built on them drifts with them.

Where everything reads from

The main file the log update maintains is Active State — ECB's single source of truth. When an agenda pulls your P1 tasks or an MIR checks what's overdue, that's the file it reads. So a stale Active State quietly makes every agenda and MIR stale too; keeping it current is the whole point of the update.

What it actually does

On each run, Claude scans the sources, cross-checks everything against the existing files, shows you a summary of what changed, waits for your okay, and only then rebuilds the files. It never deletes anything — completed tasks and resolved risks move into the archive rather than disappearing — and it never invents a completion or a decision that wasn't actually confirmed.

The two files it maintains

A log update rebuilds two of ECB's three project files. The third — Master Context — holds slow-moving company facts and is updated separately and rarely, through its own process. See the Master Context guide for that.

ECB_Active_State
Current operational reality — open tasks by priority, risks, pending decisions, standing rules. The single source of truth, read by every agenda and MIR. Changes constantly.
ECB_Decision_Archive
The permanent historical record — every decision, completed task, and resolved risk, kept forever. Append-only: nothing is ever edited or deleted, only added to.

When a task completes, it moves out of Active State and into the Decision Archive. When a decision is made, it's logged in the archive. Nothing is lost — the archive is the company's full history, and Active State stays lean by holding only what's live.

Nothing is ever deleted

The log update is additive only. It never erases anything — completed tasks move to the archive, superseded decisions get a new entry that references the old one, resolved risks are filed rather than removed. Every version of the files is a fuller record than the last, never a replacement that loses history. If you ever can't find something, it's been archived, not deleted.

When it runs

After every meeting, once that meeting's MIR has been generated.

The order is fixed: MIR first, then log update. The MIR is one of the sources the log update reads, and the end of the meeting (the "close") gets recorded too — that's the last 15 minutes of a Thursday or ad hoc session where the team reads the MIR aloud and confirms the decisions and actions. Running the log update after everything is finished means it captures that closing discussion as well as the meeting itself. The MIR guide covers that sequence.

It's not only for meetings, though. Run a log update any time the files have fallen behind reality — after a heavy work session, or when a real decision got made in Slack or a chat that the files don't yet reflect. If something changed and the project files don't show it, that's the cue to run one.

In practice that means a rough cadence of twice a week minimum — once after the Monday stand-up and once after the Thursday session — plus the occasional extra run when an ad hoc session or a big async decision lands in between. It's not a daily chore; it's "whenever the files would otherwise go stale."

Where it sits in the cycle

Meeting → MIR → log update → next agenda. The log update is the step that turns a finished meeting into updated files, so the next agenda is built on current information. Skip it, and the next agenda is working from stale data.

How to run one

Normally Aaron runs this. The flow is: trigger it, let Claude scan, review the summary, confirm, then upload the new files.

Whose job this is

The log update is Aaron's job by default — he owns the project files and runs the update after meetings, usually the same night. If you're not Aaron, you don't normally need to do this. The one exception — Aaron away, can't wait — is covered at the end of this section under running it yourself.

1

Open a new chat and turn on the connectors

Start a fresh chat in the ECB project. The log update needs Fireflies (to read transcripts) and Zapier (to scan Slack) turned on. Toggle them on via the + → Connectors, and off again when you're done. Sonnet is fine. Connector basics are in the Claude usage guide.

2

Type a trigger phrase

Any of these starts it: run log update, update the log, full scan, do a full scan, or update active state and decision archive. Claude first checks it can reach each source, then scans Fireflies transcripts, all the Slack channels, and recent chats since the last update.

3

Read the ingestion summary

Before building anything, Claude shows a summary of everything it found: tasks added, updated, or completed; decisions logged; risks changed; any conflicts; and the flags from its scan of the task list. This is your chance to catch anything wrong before it's written. It looks roughly like this:

Log update summary — 2 June 2026
Sources scannedFireflies (Thu work meeting) · Slack · chats
Tasks added1 — ECB-0xxx [new task name]
Tasks updated3 — status changes on three open tasks
Tasks completed1 — confirmed in the meeting transcript
Decisions logged1 — [one-line decision summary]
Risks added/updated1 — [risk summary]
Conflicts flagged0
Active scan flags
OVERDUE · [task past its deadline]
BLOCKER · [person waiting on another person for something]
Review the above. Confirm to generate files, or flag anything to correct first.

If anything's off — a task marked done that isn't, a decision logged wrong — you catch it here, before any file is written.

4

Confirm — or correct first

Claude waits for your okay before generating the files. If the summary looks right, confirm and it builds them. If something's off, tell Claude what to fix and it re-checks before proceeding. Nothing is written until you've confirmed.

5

Swap the files — delete the old, then upload the new

Claude produces two updated markdown files — download them, then swap them into the project. Delete the old versions first, then upload the new ones — that order avoids any risk of removing the fresh file by accident. The system relies on there being exactly one Active State and one Decision Archive file; leaving old copies behind makes Claude read stale data. Here's exactly where to do it.

The upload-and-delete routine

1. Delete the old files first. Hover over the current Active State and Decision Archive cards, and click the × on each to remove them. Doing this before uploading means there's only ever one of each file on screen — no risk of deleting the new version by mistake.
2. Upload the new files. Click + on the Files panel and add the two files Claude made.
3. Check the result. Exactly one ECB_Active_State and one ECB_Decision_Archive should remain. The date in the filename is just for reference — what matters is there's only one of each.

If nothing changed

If the scan finds nothing new since the last update — no new tasks, decisions, completions, or risks — Claude won't generate files for the sake of it. It'll just report that nothing changed and there's nothing to upload. A new file version only appears when something actually moved.

If you're not Aaron — running it yourself

This is Aaron's job, and normally you won't need to touch it. The one exception: if Aaron is away and a log update genuinely can't wait — a meeting's outcomes need to be in the files before the next session — Ori or Brendan can run it. The steps are exactly the ones above. Two things matter most when you're standing in:

The two things to get right

Review the summary honestly before confirming (step 4). You're standing in for Aaron — if something looks wrong, don't wave it through. Ask Claude to fix it first.

Swap the files in the right order (step 5). This is the easiest step to get wrong. Delete the old Active State and Decision Archive first, then upload the new ones — so exactly one of each remains and you never risk deleting the fresh version.

When in doubt, leave it for Aaron

If it's not urgent, it waits until Aaron's back. Only run it yourself when the next meeting genuinely needs current files and Aaron can't get to it. Unsure whether it's needed? Ask in #p1-important.

If something goes wrong

Claude says a source is unavailable

At the start, Claude checks it can reach Fireflies, Slack, and past chats. If one comes back unavailable, it's almost always a connector that's off — check Fireflies and Zapier are both on, then ask Claude to retry the access check. If a source genuinely can't be reached, Claude will ask whether to proceed without it; only do that if you're confident nothing important is in that source. For Fireflies specifically, the Fireflies guide covers capture and access.

The summary marks something done that isn't

Don't confirm. Tell Claude which task is wrong — it won't mark a P1 task complete without a meeting or transcript confirming it, so if one slipped through, flag it and have Claude correct the summary before generating files.

There are two of the same file in the project

This means an old version wasn't deleted after a previous upload. Keep the newest one (check the date in the filename) and delete the older. The system needs exactly one Active State and one Decision Archive — duplicates cause Claude to read stale data.

It's been a while since the last update

If the files look badly out of date, it likely just means an update was skipped after a recent meeting. Run one now — Claude scans back to the last update date, so it'll catch everything since, not just the most recent meeting.
