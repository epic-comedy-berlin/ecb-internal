What Master Context is

Master Context is the file that holds ECB's foundational facts — what the company fundamentally is. It covers the shows, the team and who does what, the brand and tone rules, the venues, the strategic targets, the hard constraints, and the core principles.

It's the slowest-moving of ECB's three project files. Where Active State changes constantly and the Decision Archive grows after every meeting, Master Context is meant to sit still — it only changes when something structural about the company actually shifts. That stability is the point: it's the steady reference everything else is measured against.

The cardinal rule: bias toward not changing it

The value of Master Context comes from being stable. If it gets updated with every operational detail, it stops being a reliable foundation and becomes just another task log. So the default answer to "does this belong in Master Context?" is no — and most months, an update finds nothing to change at all. That's the system working correctly, not a failure.

The filter — what belongs

This is the whole skill of a Master Context update: telling a foundational change apart from ordinary activity. Almost everything that happens in a month is activity, and belongs in the other two files — not here.

The test for any candidate change: does it alter a durable fact about what ECB is? Not "did something happen" — things happen constantly — but "has the foundation actually shifted."

Belongs in Master Context
  • A venue permanently added, changed, or ended
  • A show permanently added, ended, or fundamentally reformatted
  • A team role or responsibility change
  • A platform migration that is complete (not in progress)
  • A strategic target or six-month goal change
  • A brand position, tone rule, or tagline change
  • A hard constraint added, removed, or changed
  • A confirmed answer to a long-standing open question
Stays in the other files
  • Task status, progress, or completion
  • Deadlines and scheduling
  • Anything "in progress" or "being worked on"
  • Risks and blockers (unless they become permanent facts)
  • Operational decisions that don't change what ECB is
  • Meeting outcomes that don't shift a foundational fact
  • Decisions still under discussion
The tie-breaker

If you're genuinely unsure whether something is foundational or just operational, leave it out — but flag it in the proposal as a "candidate" so the decision is made on purpose rather than by omission. The "in progress vs complete" line catches most of it: a platform migration being worked on is operational; the same migration once finished is a foundational fact. Same event, different stage, different file.

What happens to facts that are no longer current

When something stops being true — you exit a venue, retire a show format, end a partnership — it doesn't just silently vanish. There are two outcomes, and the difference matters:

Retired to "Past Assets." If the old thing has reuse or reference value — a show format you might revive, a venue relationship worth remembering — it moves to a clearly-marked Past Assets section at the bottom of the file, kept for context rather than deleted. The current sections stay lean and accurate; the knowledge isn't lost.

Removed entirely. If it has no current truth and no real reference value, it's removed — and the Decision Archive still holds the decision trail for why. So nothing important is ever truly lost: it's either current, retired for reference, or recorded in the Archive.

When it runs

About once a month — specifically after the monthly review meeting (which replaces the last Thursday work session of the month) — and always after that meeting's log update, never before.

The order matters because of where the changes come from. A Master Context update doesn't scan meetings or Slack — it reads the Decision Archive (the permanent record of decisions) to find what has genuinely changed. That archive only gets current when a log update runs. So if a meeting just happened and hasn't been logged yet, the log update has to run first, otherwise the Master Context update is reading from stale information.

The order, plainly

Log update first (so the Decision Archive is current) → then Master Context update (which reads that archive). If you're not sure the archive is up to date, run a log update first, or ask. The Log Update guide covers that step.

No connectors needed

Unlike the log update, a Master Context update reads only the project files — it doesn't touch Fireflies or Slack. So all connectors should be off for this one. Nothing to toggle on.

How to run one

Aaron's job, run monthly. Trigger it, read the change proposal, confirm what's genuinely foundational, then upload the file — if anything changed at all.

Whose job this is

This is Aaron's — he maintains the project files. It's run about once a month, right after the end-of-month monthly review meeting (and its log update). There's no fallback path worth documenting here the way there is for the log update; if it needs doing and Aaron's away, it can almost always wait, because Master Context rarely needs changing.

1

Make sure the log update ran first

The update reads the Decision Archive (its primary source for what's changed) and cross-checks Active State for any operational fact that has now become permanent — so both need to be current. They're current once the latest meeting has been logged. If the log update has run since the last meeting, you're good; if not, run it first. See the Log Update guide.

2

Open a new chat and trigger it

Start a fresh chat in the ECB project, with all connectors off (this update reads project files only). Then type any of these to start it: update master context, update the master context, or master context update. Claude reads the current Master Context, then the Decision Archive since the last Master Context update, applying the filter to everything it finds. Sonnet is fine.

3

Read the change proposal

If Claude finds anything foundational, it presents a proposal — grouped by section, each row labelled CHANGE, NEW, REMOVE, or RETIRE (moved to Past Assets rather than deleted), and every row traced to a dated decision in the archive. Anything borderline is flagged as a "candidate" for you to rule in or out. It looks roughly like this:

4

Confirm what's genuinely foundational

This is your judgement call. Confirm the changes that truly belong, reject anything that's really operational, and rule on the candidates. If a proposed change isn't quite accurate — wrong wording, a detail off, missing nuance — correct it before confirming rather than waving it through; what you confirm is what gets written. Claude waits for your okay and applies only what you confirm, editing those specific facts and leaving the rest of the file exactly as it was.

5

Swap the file — delete the old, then upload the new

If changes were confirmed, Claude produces an updated ECB_Master_Context file. Swap it into the project the same way as any project file: in the Files panel (right side of the ECB Company Work project), delete the old Master Context first, then upload the new one — so exactly one remains. The Log Update guide shows the Files panel and the delete-then-upload routine in detail.

The usual outcome: nothing changes

Most months, a Master Context update finds nothing foundational and produces no new file. This is expected — it's the system working as designed.

When that happens, Claude won't generate a file for the sake of it. It reports that the Decision Archive since the last update was reviewed, everything in it was operational, and Master Context is unchanged — nothing to upload. A new version of the file should be a genuinely rare event.

If every month produces changes, something's off

If Master Context is changing every single month, that's a sign the filter is being applied too loosely — operational detail is leaking into the foundation file. When in doubt, the answer is "leave it out." A foundation that shifts constantly isn't a foundation.

If something goes wrong

Claude can't read one of the files

A Master Context update needs three files: the current Master Context, the Decision Archive, and Active State. If Claude can't retrieve one, it stops rather than working from memory. Usually this means a file is missing or duplicated in the project — check the Files panel has exactly one of each, then try again. The Log Update guide shows where the Files panel is.

The proposal includes something operational

If a proposed change is really just task progress or an in-progress item dressed up as a foundational fact, reject it. Tell Claude it's operational and belongs in Active State, not Master Context. The filter isn't perfect — your judgement on what's genuinely foundational is the final call.

You're not sure the Decision Archive is current

If a meeting happened recently and you're not certain it's been logged, the archive may be missing the latest decisions — which means the Master Context update could miss a real change. When unsure, run a log update first, then come back to this. See the Log Update guide.
